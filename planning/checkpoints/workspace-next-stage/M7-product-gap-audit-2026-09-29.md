# Product-facing gap audit — M5–M7

**Date:** 2026-09-29  
**Scope:** user journey from opening the project app through login/session, Jobs/Review/catalog, MT5 report/replay, connector destination selection, and durable status/recovery.  
**Method:** source inspection plus focused frontend build/contract checks. This is an audit receipt; it does not promote M5, M6, or M7.

## Executive result

The product has a usable **local/offline skeleton** and the selected UI paths are wired enough to demonstrate the intended flow. It is not yet a complete product because the project login is simulated or local-trusted, the connector state/receipt is held only in browser memory, and no external OAuth/dispatch/reconcile path is connected to the project backends. M5 remains PREP_ONLY for the same reason stated in the plan: the code and fixtures exist, but real authorized-media/persistence and product acceptance are still open.

## Highest-impact product gaps

1. **Identity is not a product identity yet.** The VI “Sign in to project (demo)” is a reducer transition, while MT5 trusts a server-configured local identity and a URL/header workspace. This is suitable for local development but cannot safely own cloud connections or multi-user data.
2. **Connector UI is a state-machine demo, not a connector.** It correctly prevents accidental I/O and is useful as a contract oracle, but it intentionally cannot authorize, upload, dispatch, query an unknown result, or revoke a real connection.
3. **Connector receipts are not durable.** Closing/reloading the browser loses the pending intent/receipt in both apps. This also means there is no user-visible queue or recovery path for timeout/crash/offline cases.
4. **M5 persistence primitives are ahead of their product surface.** SQLite catalog/recovery/relink code and tests exist, but the API exposes only a read view; the user cannot rebuild, restore, or relink from the app, and no real-media product acceptance has been recorded.
5. **Review mutation errors are not surfaced consistently.** VI applies local optimistic edits before the request and has no rollback/toast/inline error state for failed PATCH, batch accept, or rerender. A network failure can leave the visible state different from the durable job.

## Recommended implementation order

1. **Product session boundary:** define one local/demo session contract first (identity, project/workspace, expiry, sign-out), then make both UIs consume it. Keep external provider login separate.
2. **Durable connector ledger:** add project-owned connection, intent, receipt and event records with `connection_id + epoch`, source revision/hash, idempotency key, status (`pending|unknown|succeeded|failed|revoked|cancelled`) and reconcile metadata. Restore this state before showing a connector panel.
3. **VI M5 recovery surface:** expose rebuild/status/relink/backup/restore as explicit local actions, then run the real authorized-media Jobs→Catalog→Review→export journey with revision/checksum assertions.
4. **One real external connector at a time:** after exact account/destination/data scope is provided, wire Drive first (bounded `drive.file` copy), then Notion; use read-only profile/capability probes before any write. Keep Learn local until its owner service is specified.
5. **Failure UX and acceptance:** add retry/unknown/revoke controls and browser tests for reload, timeout, duplicate click, stale revision, provider denial, partial upload and revoke fencing. Only then refresh M7 integrated traceability.

## Validation performed

- VI frontend: `npm run build` passed; `npm run test:connector-flow` passed (`27` checks); `npm run test:ui-contract` passed (`4`); `npm run test:telemetry-contract` passed (`5`).
- MT5 frontend: `npm run build` passed; `npm run test:notion-connector` passed (`4` tests).
- Existing MT5 Playwright acceptance scripts were source-reviewed for the report/replay/Notion paths; they cover the functional offline fixture but do not perform OAuth/Notion/cloud I/O.
- No provider, broker, OAuth, upload, or external write was performed during this audit.

## Decision

Keep current M5/M6/M7 labels **PREP_ONLY / ACCEPTED-SCOPED where already recorded**. The missing items above are product implementation work, not a reason to weaken the safety boundary or treat the offline demos as real integration.
