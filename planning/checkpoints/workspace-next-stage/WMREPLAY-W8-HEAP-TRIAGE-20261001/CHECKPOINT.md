## How the current gate is calculated

The harness launches Chromium with `--js-flags=--expose-gc` (`audit_soak.mjs:121-125`). Every 15 iterations it reads `performance.memory.usedJSHeapSize`, calls `window.gc()` when available, then reads `usedJSHeapSize` again as `afterGcHeap` (`audit_soak.mjs:222-241`).

The reported delta does **not** use the initial navigation sample. It selects the first non-null `sample.afterGcHeap` and the last non-null `sample.afterGcHeap`, then computes:

```text
heapDeltaBytes = lastAfterGcHeap - firstAfterGcHeap
heapGrowthPerMinuteBytes = heapDeltaBytes / (Date.now() - sessionStarted) * 60,000
```

This is implemented at `audit_soak.mjs:275-279`. The initial sample stores the value read before its first `gc()` (`audit_soak.mjs:187-200`), but that value is not selected for `heapDeltaBytes` when a sampled `afterGcHeap` exists.

The post-GC series has large saw-tooth jumps and drops, then long plateaus; DOM and rendered-row counts are constant; there are no interaction or runtime errors. That pattern is compatible with V8 heap growth/allocator pages and delayed collection, plus repeated allocation from rebuilding/filtering a 5,000-row analytics model. It does **not** prove that product state is released: the final post-GC value remains 40.9 MB above the first sample, and `performance.memory.usedJSHeapSize` is not a heap snapshot or retained-object graph.

The harness did not record a navigation event, so this cannot be attributed to a reload. It does not change the heap delta formula, but it makes per-sample elapsed values unsuitable for leak attribution until navigation/time-origin events are logged.

Therefore: keep the W8 heap acceptance **open**. Do not label this as a confirmed leak or dismiss it as GC noise from this receipt alone.
